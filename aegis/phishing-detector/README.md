# Explainable Phishing URL Detector

A URL-based phishing detector that prioritizes **explanation over a bare score**: rather than "94% malicious," it reports *which structural features* of the URL drove the decision, in plain English — excessive subdomains, a brand name used as a subdomain instead of the real domain, an uncommon TLD, missing HTTPS, and so on.

Four approaches are trained and compared head-to-head: **rule-based → logistic regression → random forest → neural network**, evaluated on precision, recall, false-positive rate, and — the more interesting result — robustness to adversarial typosquat URLs that deliberately avoid the obvious signals.

**Data note:** all URLs used here are synthetically generated (`data/generate_dataset.py`) from well-documented structural patterns phishing campaigns are known to use (IP-literal hosts, brand lookalike subdomains, suspicious TLDs, keyword stuffing, homoglyph substitution). No real phishing URLs are scraped, stored, or distributed by this project.

## Methodology

**Features** (15 total, all computed purely from the URL string — no live network/WHOIS lookups): URL length, dot/hyphen/digit counts, subdomain depth, IP-literal host, HTTPS presence, suspicious TLD, urgency-keyword count, brand-in-subdomain-not-domain, path entropy, `@`-symbol obfuscation, non-standard port, digit/letter substitution pattern, query length.

**Models:**
- **Rule-based**: a hand-tuned weighted sum over the same 15 features, thresholded. No training — this is the "what would a simple heuristic catch" baseline.
- **Logistic Regression**: linear model on standardized features — gives directly interpretable signed coefficients.
- **Random Forest**: 200 trees, max depth 8 — captures feature interactions the linear model can't.
- **Neural Network (MLP)**: two hidden layers (32, 16) — the most flexible of the four, and (as the results below show) the one that overfits most to the synthetic training distribution's surface patterns.

**Explanation layer:** each model's per-feature contribution is ranked by magnitude, but the *direction* ("increases" / "decreases" risk) is assigned from a fixed domain-knowledge table rather than from each model's raw internal signal — Random Forest feature importances and the MLP proxy used here are magnitude-only, so deriving a direction from them directly would occasionally mislabel protective features (e.g. it initially mislabeled "HTTPS present" as risk-increasing until this was caught and fixed during testing; see note below).

## Results

Run `models/train.py` to regenerate these (results also written to `dashboard/results.json`):

| Model | Precision | Recall | F1 | False Positive Rate |
|---|---|---|---|---|
| Rule-based | 0.921 | 1.000 | 0.959 | 0.085 |
| Logistic Regression | 1.000 | 1.000 | 1.000 | 0.000 |
| Random Forest | 1.000 | 1.000 | 1.000 | 0.000 |
| Neural Network | 1.000 | 1.000 | 1.000 | 0.000 |

On the in-distribution held-out test set, all three ML models reach perfect separation — expected, since the synthetic generator's phishing/legit patterns are quite structurally distinct and the dataset is clean and balanced.

**The more informative result is the robustness test.** `models/train.py` also generates 300 *adversarial* phishing URLs — single-character brand typosquats (e.g. `paypaI.com`, `micros0ft.com`) that deliberately use HTTPS, a common `.com` TLD, no urgency keywords, and shallow subdomain depth, i.e. they strip out every "loud" signal the training distribution leans on:

| Model | Recall on adversarial typosquats |
|---|---|
| Rule-based | 0.477 |
| Logistic Regression | 0.000 |
| Random Forest | 0.477 |
| Neural Network | 0.000 |

Both linear-on-raw-features approaches (logistic regression, and the MLP which is also trained on the same scaled feature set) **completely fail** to catch typosquats once the obvious lexical red flags are removed — their 100% in-distribution accuracy was partly a memorized shortcut ("urgent keyword present" / "odd TLD present"), not real generalization to the actual phishing concept (impersonating a brand's domain). The rule-based and random-forest approaches do only moderately better (~48% recall), because neither has a feature that directly measures "is this domain a near-miss of a known brand name" — character-level edit distance to a brand list would be the natural next feature to add, and this gap is exactly the kind of finding an explanation-first project is supposed to surface.

**Top contributing features** (see the dashboard for full charts): `urgent_keyword_count`, `suspicious_tld`, `brand_in_subdomain_not_domain`, and `has_ip_host` dominate the Random Forest's importances and the Logistic Regression's coefficients — consistent with the robustness gap above, since none of those fire on a clean single-character typosquat.

## Running It

**1. Train the models** (from `phishing-detector/`):
```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python3 models/train.py
```
This regenerates the dataset, trains all three ML models, saves them to `models/artifacts/`, and writes `dashboard/results.json`.

**2. View the dashboard:** open `dashboard/index.html` directly in a browser (it fetches `results.json` from the same folder).

**3. Run the inference API:**
```bash
uvicorn api.main:app --port 8010
```
Then `POST /predict` with `{"url": "...", "model": "random_forest"}`.

**4. Load the Chrome extension:**
- Go to `chrome://extensions`, enable Developer Mode, click "Load unpacked," select the `extension/` folder.
- Make sure the API is running on `localhost:8010` (step 3), then click the extension icon on any page to see a live verdict + explanation for that tab's URL.

## Tests

```bash
python3 -m pytest tests/ -v
```
Covers feature extraction correctness (IP-host detection, HTTPS detection, suspicious TLD, keyword counting, subdomain depth) and the rule-based classifier's behavior on clean examples at both ends of the risk spectrum.

## Limitations & Future Work

- The dataset is synthetic; real-world phishing campaigns are more varied than six procedural templates, so absolute precision/recall numbers here should be read as a methodology demonstration, not a production accuracy claim.
- The robustness gap identified above points directly at the next feature to add: a brand-name edit-distance feature (Levenshtein distance from the registrable domain to each entry in a known-brand list) would likely close much of the typosquat gap without needing a larger model.
- "Domain age" is modeled only as a lexical proxy (no live WHOIS lookup) by design, to keep this project free of any live external queries.
